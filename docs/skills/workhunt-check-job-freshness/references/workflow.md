# Check freshness workflow

The shared qualifier applies source-specific windows only when both `run_type` and `execution_context` are `manual`. Read the private `search_brief.manual_source_freshness_hours` and optional `manual_freshness_policy`; shared defaults are empty. At a new run, fix one anchor instant, subtract elapsed hours in UTC and express bounds in the configured IANA time zone, including clock changes. Save the bounds, time zone, source windows, policy and requested minimum together. A configured `employer_registry` or `techmap` exception requires the exact opportunity ID and listing URL paired in one identity or explicit alias, a public provenance URL, textual membership evidence and an aware, nonfuture observation time. A later membership observation does not move the publication anchor. Unsupported membership falls back to that saved run's `other` window, normally 24 hours for a new run; discovery/feed update times and a cross-post alone do not prove membership or freshness. Saved bounds and policy remain authoritative when the current profile changes. Collector, notification, assessment and fixture contexts always use exactly 24 elapsed hours, including legacy scan runs. Settings do not authorize execution. Record original publication, update/repost, feed/alert availability, first discovery, deadline and verification as distinct events with raw text, source URL and precision. Original publication OR a genuine evidenced refresh/repost inside the window can qualify. An older original date does not cancel a recent valid refresh. Discovery/crawl/check time and malformed relative labels do not qualify. Date-only or relative evidence needs its whole supported interval inside the window; never invent an hour. Preserve contradictory or future-dated evidence as unresolved. Source-specific semantics apply only to the observed channel. Reposts retain identity and exclusions. A proposed check is not a live observation; no schedule or API run is implicit.
