# Private profile contract

`profile.json` is an empty shared contract until private evidence is mapped. Keep unknown scalar values null or empty and unknown collections empty. `configured` remains false until explicit search settings validate.

- `name`, `headline`, `identity`, `capabilities`, `experience`, `education`, `languages`: supported facts with evidence references. Capability `duration_years` may be null. Education `completed` is true only with evidence.
- `tracks`: user-selected keys, each with an English/internal `label`, restrictive `title` regex and nonempty `stack_all` capability regexes. Result language is separate. `search_brief.tracks` names selected keys; `required_stack` names review capability keys.
- `eligible_countries`: explicit identifiers/aliases for candidate-country checks. `location_pattern`: restrictive location regex; ambiguous abbreviations need explicit context. `timezone`: IANA name. `language`: explicit result language.
- `limited_experience`: evidence-backed technology-to-years caps only. Unknown duration must not create a cap. `degree_policy` records accepted qualifications and explicit alternative policy; per-listing `degree_status` still needs evidence.
- `preferences`: explicit work modes, relocation, availability and commercial constraints only. Unknown preferences remain null/empty.
- Source enable flags default false. `extra_boards`, directory URL and source paths are explicitly selected. `employer_registry` resolves a private registry first, then a shared seed at the same relative path. `employer_overrides` and `source_health_file` always resolve inside `.workhunt/`. `matching_aliases` are user-confirmed regex/replacement pairs for discovery; they do not rewrite the original advertisement.
- `cv_manifest` selects a private manifest path; it must not collide with canonical histories, configuration or legacy inputs. Versions retain measured path/hash/timestamp, version ID, supported language/role mapping, selection status, exact-file content-review evidence and unresolved facts. The empty shared manifest contains no versions. Hash equality is not content review or upload authorization.
- `search_brief`: run type, requested minimum (null when not requested), optional cap and explicit capability keys. Optional `manual_source_freshness_hours` and `manual_freshness_policy` are empty objects in every shared example. Only explicit user decisions may populate source exceptions and adoption provenance privately. Shared profiles omit `source_windows`, `window_start` and `window_end` entirely: create those fields at a new run or preserve a valid saved snapshot, never insert empty/null placeholders. Both `run_type` and `execution_context` must be `manual` for configured, evidenced source windows; collector, notification, assessment and fixture contexts remain 24 hours. Saved snapshots preserve their bounds, source policy, time zone and requested minimum instead of inheriting today's profile. Saved evidence is not current authorization.

Canonical history lives in `data/jobs.json` and `data/applied_jobs.json` beneath `.workhunt/`. Setup does not invent empty histories when an existing history is unknown. The optional helper never deletes those records and refuses to overwrite existing populated profile outputs without a reviewed update implementation.

Review fields use `geography.eligible`, `geography.eligible_from`, and supporting evidence; `degree_status` can be mandatory_met, mandatory_no_alternative (unmet), experience_equivalent, preferred, not_stated or ambiguous. A source listing alone does not supply these assessments.

Loading historical data is distinct from creating a new profile brief. Only a new profile brief or a saved snapshot explicitly marked `execution_context: manual` may derive source windows from preferences. For an exact copied legacy brief, recover context only from unambiguous canonical snapshots with consistent context, policy, time zone and bounds. Inferred manual context alone does not activate dormant mappings. Unknown or conflicting manual history stays `unresolved` at its recorded base bounds; supplied source-window evidence is retained separately as `recorded_source_windows`. Keep `context_provenance` and matching run IDs inside private records/packets. Preserve original provenance and `recorded_source_windows` through normalization, JSON save/reload and packet preparation; `context_resolution` describes the current normalization separately. Neither provenance field grants permission or activates preferences. Do not invent manual markers or silently replace contradictory supplied bounds. Explicit collector, notification, assessment and fixture behavior remains 24 hours.

`work_location_policy` is a current preference, separate from historical run snapshots. Shared fields are `base_country: null`, `work_path: null`, `exclude_required_foreign_conditions: []`, `unknown_eligibility: null`, `candidate_legal_status: "unknown"` and `provenance: {}`. Country uses an explicit two-letter code; work path is the user's explicit identifier. Unknown handling selects `needs_clarification` or `exclude`; neither option permits unverified eligibility. Exclusion condition keys are `work_visa`, `work_permit`, `right_to_work`, `residency`, `relocation`, `office_only` and `travel`. A decision may explicitly choose an empty exclusion list; mandatory unresolved conditions still cannot qualify.

Only a sourced user-confirmation decision may fill work-location preferences. The helper records its source ID, locator and evidence privately. CV location, employer country and missing facts never populate policy or legal status. Assessment `work_eligibility.work_path` contains `{base_country, work_path, status, evidence}`; both scope values must match current policy. Legacy country-specific evidence is preserved as private raw material, never silently interpreted for another country/path. Exact-listing evidence, constraints and authorization basis still need review. Supported basis values distinguish `not_stated_full_ad`, `explicit_no_foreign_requirement` and `employer_confirmation`; none infers candidate permits.

## Explicit client-project alternatives

Employment and employee-style contracts retain the saved `required_stack`. A separately confirmed `search_brief.project_stack_policy` may select buyer-project alternatives. The shared default is `{"configured": false, "alternatives": [], "provenance": {}}`; it enables nothing. A configured alternative has a nonblank `id`, nonempty `required_capabilities` and `discovery_patterns` with one restricted private regex per capability key. Patterns and keys are candidate choices, never inferred from CV facts or supplied by a default technology. New authorized manual/assessment/collector/notification/fixture briefs copy the policy; saved briefs retain exactly their own policy or its absence. Current work-location policy still applies separately to historical assessments.

Discovery may retain a generic project title or incomplete description as `provisional_project_hint` when configured patterns match; it does not qualify the lead. Final alternate-stack scope requires `project`/`paid_project`, or a `contract` with explicitly evidenced `engagement_type: client_project`; an identified project/invitation, selected `projects` track, reviewed stack capability flags and exact buyer `project_scope` evidence must all agree. Scope records `paid_client_work: true`, nonblank deliverables/evidence, the exact listing `source_url` and `capabilities` keyed identically to the selected alternative. Tags, bidder prose, platform identity, seller services and generic admission cannot supply that evidence.

`stack_check.path: client_project_alternative` records the selected `alternative_id`, capability keys and private buyer evidence. All actual mandatory requirements, including backend work, remain in the unchanged 75% fit denominator; the employment backend is not invented as a project requirement. Degree/limited-experience, full-description, current geography/work eligibility, freshness, route and history gates remain independent. A hidden buyer name can stay unknown when an exact marketplace `source_job_id` or `project_id` identifies the brief. A separate proposal form needs the named owner or exact `project_id` plus paired listing/navigation/identifier/time evidence; two absent names never establish ownership.

Compatibility is interpretation only: explicitly recorded legacy `angular_frontend_without_dotnet: true` and matching legacy `angular_frontend` buyer evidence keep their historical meaning. No legacy choice is inserted into empty policies. Explicit generic `configured`/`alternatives` fields take precedence, and an explicit generic `capabilities` map cannot be overridden by a legacy flag. Saved raw policy and provenance remain unchanged. Legacy discovery spellings are available only under that recorded legacy choice or explicit private patterns/aliases.

In manual reports, show every new promising project within the selected project policy with evidenced fit of at least 75% but unresolved independent gates in a separate visible unverified note. Give score/gaps, exact link, missing evidence and the next check. Count zero qualified matches and provide no recommendation letter for it. This is manual guidance, not an automatic renderer feature, changed notification silence or a new alert. Filled policy/adoption provenance, `project_scope` and `stack_check` belong only in private records, packets and reports.
